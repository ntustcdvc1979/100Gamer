# 百人派對遊戲

100+ 人同時用手機連線的現場互動遊戲。投影幕跑遊戲，玩家用手機當搖桿，分隊對抗。

| 頁面 | 給誰 |
|---|---|
| `stage.html` | 投影幕。唯一做全域訂閱、負責所有運算與渲染的客戶端。 |
| `play.html` | 玩家手機。輸入名字、自己選隊，之後依關卡變成搖桿／相機／翻面／搖動／地圖／字陣。 |
| `console.html` | **主控台**。遙控投影幕、看全場分數、叫排行榜、把搗亂的人請出去。限定指定的 Google 帳號。 |
| `index.html` | 入口。QR code 與開場前檢查清單。 |
| `server/` | 遊戲伺服器。純中繼，跑在 Fly.io 東京。 |

沒有房號。掃到的 QR 就是入口，少一個現場會出錯的環節。

## 十個遊戲

順序刻意在「坐著」與「站起來」之間交替，不要連續兩關都在狂搖：

| | 遊戲 | 型態 | 玩家在做什麼 |
|---|---|---|---|
| 1 | **聚沙成塔** | 全體協作・搖桿 | 把光點推進投影幕上鏤空的字裡面填滿。沒有輸家，目的是學會操作 |
| 2 | **四方拔河** | 分組對抗・搖桿 | 大球在中間，四隊各自往自己的顏色區推 |
| 3 | **選邊站** | 個人賽・搖桿 | 畫面分四象限，移到自己的選擇。有答案的答對得分，沒答案的少數派得分 |
| 4 | **搖拔河** | 兩場同時・搖手機 | 上半場紅 vs 黃，下半場綠 vs 藍。搖一下拉一下 |
| 5 | **地理達人** | 個人賽・點地圖 | 出一個地名（可配照片），30 秒內在台灣地圖上點位置，差幾公里決定分數 |
| 6 | **文字找不同** | 個人賽 | 滿滿的「人」裡藏一個「入」，越快點到分數越高 |
| 7 | **搖賽跑** | **團體賽**・搖手機 | 橢圓跑道，全隊次數累加推同一個角色，跑兩圈。一圈的下數可在主控台調 |
| 8 | **拍照找顏色** | 個人賽・60 秒 | 找一個最像「蘋果紅」的東西拍下來。可重拍，只能上傳一次 |
| 9 | **拔蘿蔔** | 分組對抗・**拉手機** | 一分鐘，往上一拉拔一根，蘿蔔會從田裡飛出去。哪一隊拔最多 |
| 10 | **火候達人** | 個人賽・六道菜 | 在指定秒數翻面／提起／晃動。投影幕的秒數兩秒後會淡掉，要自己數 |
| 11 | **總排行榜** | 頒獎 | 從第十名往上一個一個揭曉，同時列出四隊總分。可以停著讓大家拍照 |

十一關全開約 50 分鐘，不用全部跑完 —— 主控台可以跳關。
分數跨關卡累計，主控台隨時看得到，<kbd>L</kbd> 可以隨時蓋一層排行榜上去，
最後一關則是完整的頒獎畫面。

主控台還可以：**編輯地理達人的題目與照片**（照片只上投影幕，不傳到手機）、
**調搖賽跑一圈要幾下**、**把搗亂的人請出去**。
設定與題庫會送給所有關卡，所以可以在別的關卡時先準備好。

**玩家自己選隊**，加入時看得到各隊人數（不然一定有一隊爆滿）。
主控台可以把搗亂的人請出去。

幾個設計上的堅持：

- **四方拔河與搖拔河的隊伍力量用「平均」不是「總和」。** 現場一定會有人
  中途離線、有人手機沒電。用總和的話人多的隊直接贏，比賽就沒意義了。
- **搖賽跑相反，刻意用總和**（那是這一關的玩法：全隊一起累加）。
  所以畫面上會寫出每一隊幾個人，主持人看得到要不要調人或調一圈的下數。
- **搖拔河是兩場 1v1 而不是一場 2v2。** 四隊擠一條繩子的話，
  紅隊的人根本分不出來是自己拉贏還是黃隊拉贏。
- **拔蘿蔔用拉的不是搖的。** 連三關都在甩手很膩，而且「拔蘿蔔」的體感
  本來就是往上拔。判定門檻和冷卻都跟搖不一樣 —— 用同一組參數的話，
  狂甩的人會被當成在狂拉。
- **四方拔河畫面上要顯示「參與率」。** 這一關好玩的地方不是體力，
  是看到自己隊上有八個人在放空 —— 那個數字會讓全隊自己吼起來。
- **搖動送的是累計值不是增量。** input 會被攤平覆蓋，中間掉幾筆很正常；
  送增量掉一筆就少算幾下，送累計值掉多少筆都補得回來。
- **拍照只送縮圖（200px、約 8–12KB）。** 要在投影幕上秀照片，照片就一定得
  離開手機。換成原圖是幾十 MB，會打爆 256MB 的中繼機。見下面的「資料與隱私」。
- **拍照與地理達人的分數等時間到才公布。** 邊做邊看分數的話，大家會站在原地
  微調刷分（或用二分搜尋逼近答案），而不是真的去找、去猜。
- **色差用 Lab 空間的 CIE94，地理用實際公里數。** RGB 歐氏距離跟人眼差很遠；
  「差 0.03 個畫面寬」也沒有人聽得懂，「差 12 公里」大家馬上知道差多少。
- **火候達人的秒數會淡掉，而且不畫玩家圓圈。** 這一關的樂趣就是用身體數秒，
  把碼表留在畫面上就沒了；一百個點飄在鍋子旁邊也只會擋住秒數。
- **感測器狀態要一直看得到。** 不是只看「權限給了沒」—— 有些手機權限給了
  卻不送資料。玩家要在開始之前就知道自己得改用按鈕。
- **手機上沒事不顯示搖桿。** 只有真的要用的關卡才長出來。

要加新遊戲就實作 [`src/stage/games/types.ts`](src/stage/games/types.ts) 的 `Game` 介面，
加進 [`games/index.ts`](src/stage/games/index.ts) 的陣列。**加之前先想延遲**：
端到端約 60ms，不要做需要精準時序判定的（誰先按、節奏、瞄準）。

改題目：[`config/questions.ts`](src/config/questions.ts)（選邊站）、
[`config/geo.ts`](src/config/geo.ts)（地理達人），
以及各遊戲檔案裡的 `DISHES`（火候達人）、`PROMPTS`（拍照）、
`PUZZLES`（找不同）、`SHAPES`（聚沙成塔）。

地理達人的照片放在 `public/geo/`（自己建這個資料夾），
在 `config/geo.ts` 的 `img` 填檔名就會出現。**照片會同時出現在投影幕和
一百支手機上，記得先壓過**（長邊 800px、JPEG 0.7 以內）。

### 鍵盤

<kbd>→</kbd> 下一關（遊戲可以先吃掉，例如換題目、換字）　<kbd>←</kbd> 上一關
　<kbd>T</kbd> 開始／暫停　<kbd>R</kbd> 重來　<kbd>L</kbd> 總排行榜
　<kbd>F</kbd> 全螢幕　<kbd>Esc</kbd> 關卡選單

主控台上的按鈕送的就是同一組按鍵，投影幕是唯一的真相來源。

## 開始之前

**必看** [`docs/SETUP.md`](docs/SETUP.md)：Fly.io 建置、GitHub 設定、壓力測試、現場手冊。

```bash
npm install
npm run server     # 另一個終端機
npm run dev
```

什麼都不設定就跑**本機模式**（BroadcastChannel），同一台電腦開幾個分頁就是幾個玩家。
彩排想先看 100 人的畫面長什麼樣：

```bash
npm run fake -- --clients 100
```

## 三條不能違反的規則

這個架構撐得住 100 人，靠的是**非對稱扇出**。違反任何一條，人數一上來就會卡死：

1. **手機只寫自己、只讀 `state`。** 永遠不訂閱 `players` 或 `inputs`。
   120 人互相訂閱是 O(n²) = 每秒 29 萬則訊息。
   （`room.onPlayers()` / `room.onInputs()` 在 play 角色下會直接丟例外，擋住這個錯誤。）
2. **只有投影幕做全域訂閱。** 它是唯一看得到所有人的客戶端。
3. **`state` 要小、要低頻。** 即時座標只活在投影幕的記憶體裡
   （[`src/stage/render.ts`](src/stage/render.ts)），永遠不寫回 `state`。

節流不是靠自律，是寫在 [`src/net/room.ts`](src/net/room.ts) 裡的：送出頻率依傳輸層自動套用
（見 [`src/config/settings.ts`](src/config/settings.ts) 的 `RATES`），而且內容沒變就不送。

`state` 裡唯一一個明知會變大還是放進去的欄位是選邊站的 `options`——
大禮堂後排看不清楚投影幕，四個選項一定要出現在自己手機上。四段短字約 100 bytes，值得。

除了 `state`，還有三條刻意繞開它的窄通道（見 [`schema.ts`](src/net/schema.ts)）：

| | 方向 | 為什麼不走 state |
|---|---|---|
| `action` | 手機 → 投影幕 | 拍到的顏色、翻面的時間。**不能掉** —— 搖桿漏一格沒人在乎，「我拍好了」漏掉就是這個人沒分，所以不做攤平覆蓋 |
| `command` | 主控台 → 投影幕 | 換關卡、開始、排行榜。伺服器會先驗身分才轉 |
| `scores` | 投影幕 → 主控台 | 100 列的計分表。廣播給所有手機就是白燒 100 份頻寬 |

## 傳輸層

連線層是一個介面（[`src/net/transport.ts`](src/net/transport.ts)），有三個實作。
**遊戲程式只能依賴這個介面，不准直接 import firebase 或 WebSocket。**
這道紀律已經回本過一次——從 Firebase 換成 WebSocket 時，`stage/` 和 `play/` 一行都沒改。

| | 用在哪 | 搖桿頻率 |
|---|---|---|
| `websocket.ts` | **主線**。Fly.io 東京，實測 120 人 **p95 = 59ms** | **20 Hz** |
| `firebase.ts` | 備援。RTDB 每次寫入都算錢，被迫壓低頻率 | 5 Hz |
| `local.ts` | 開發與離線降級。BroadcastChannel | 20 Hz |

降級順序：**遊戲伺服器 → Firebase → 本機模式**，投影幕永遠跑得動。

壓力測試要**拆成多個處理程序**跑，不然量到的是測試程式自己的 event loop 排隊時間：
單一處理程序打 Fly 得到 p95 = 2502ms，拆開之後是 59ms。做法見 [SETUP](docs/SETUP.md)。

## 資料與隱私

玩家只留一個名字（暱稱即可），不收任何聯絡方式。
伺服器的房間資料只活在記憶體裡，重啟就沒了。

**「拍照找顏色」會上傳照片。** 這一關的縮圖（200px）會送到伺服器再轉給投影幕，
**而且會投在大螢幕上給全場看**。原圖不會離開手機，縮圖也不落地
（伺服器只轉不存，投影幕只留在記憶體，重整就沒了），但它確實離開了手機。

手機上有寫這句話，主持人**開這一關之前也要講一次**：
拍到的東西會出現在大螢幕上，不想被看到的就不要入鏡。

有用 Firebase 備援的話，活動結束後照 SETUP.md 最後一節把資料刪掉。
